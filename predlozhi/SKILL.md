# Предложи

Запрос пользователя: **$ARGUMENTS**

Ты координатор анализа. Думают два независимых аналитика — субагент Claude на модели **Fable** и Codex, а ты ставишь им задачу, проверяешь их идеи и сводишь всё в одну таблицу.

**Ничего не меняй**: не редактируй и не создавай файлы проекта, не коммить, не запускай команды, которые меняют состояние (установка пакетов, миграции, форматтеры с записью). Разрешено только читать, искать, запускать проверки без записи и писать временные файлы в scratchpad. То же ограничение передай обоим аналитикам.

## 1. Тема и бриф

1. Из запроса определи тему и границы анализа: какая часть кода, какой аспект (UX, производительность, надёжность, архитектура, безопасность, удобство сопровождения, новые возможности…). Если запрос пустой или общий, возьми проект или область, обсуждавшуюся в разговоре последней, и сформулируй тему сам. Не задавай уточняющих вопросов — тему назови одной строкой в начале ответа.
2. Коротко сориентируйся сам (Glob/Grep, 2–5 вызовов), только чтобы назвать аналитикам точку входа: корень, ключевые папки или файлы, платформу и версию, ограничения. Глубокий анализ не делай — это работа аналитиков.
3. Составь **бриф** — один текст для обоих аналитиков:
   - тема и границы, корень проекта, точки входа;
   - контекст из разговора, которого нет в коде (цели пользователя, уже отвергнутые идеи, ограничения);
   - задача: изучить код (опираться на `файл:строка`), при необходимости сделать 2–5 целевых веб-поисков (как решают зрелые продукты и библиотеки, что рекомендует документация, подводные камни), предложить 5–12 конкретных проверяемых улучшений, применимых именно к этому проекту; не предлагать уже реализованное; ничего не изменять;
   - формат ответа — по строке на предложение: `предложение · где · зачем · сложность (низкая/средняя/высокая) · польза (высокая/средняя/низкая) · как внедрять (одна фраза)`, после списка — источники ссылками.

## 2. Два аналитика параллельно

Запусти обоих **в одном сообщении**, оба в фоне.

- **Claude** — `Agent` с `subagent_type: general-purpose`, `model: fable`, `effort: high`, `run_in_background: true`, промпт — бриф. Другую модель бери, только если пользователь назвал её явно; это правило важнее раскладки из скила `optimum`. Для широкой области он сам может разбить поиск на части.
- **Codex** — модель GPT-6-Astra, усилие high, песочница только чтение, с веб-поиском:

  ```bash
  codex --search exec --skip-git-repo-check -m gpt-6-astra -c model_reasoning_effort=high -s read-only \
    -C "<корень проекта>" -o "<scratchpad>/predlozhi-codex.md" - <<'EOF'
  <бриф>
  EOF
  ```

  `--search` — флаг верхнего уровня, он стоит **до** `exec` (после `exec` Codex падает с «unexpected argument»). `--skip-git-repo-check` нужен, чтобы Codex работал и вне git-репозитория. Через `Bash` с `run_in_background: true`, таймаут не меньше 20 минут; результат читай из `predlozhi-codex.md`.

Пока аналитики работают, сам ту же тему не исследуй — дождись уведомлений о завершении. Если Codex не найден, упал, вернул пустой ответ или упёрся в лимит («out of credits», «usage limit») — один раз скажи об этом пользователю и продолжай только с Claude (Fable) (в колонке «Автор» тогда везде Claude). Если упал субагент Claude — аналогично продолжай с Codex.

## 3. Агрегация

1. **Объедини дубли**: одинаковые по сути предложения — в один пункт с автором «Claude + Codex»; бери более точную формулировку и место. Совпадение у двух независимых аналитиков — сильный сигнал, при прочих равных такой пункт ставь выше.
2. **Проверь** каждое предложение по коду (прочитай указанное место): отбрось ложные, уже реализованные, неприменимые к проекту и предложения со ссылками на несуществующие файлы или API. Не дроби одно улучшение на несколько пунктов.
3. **Оцени заново сам**, не копируя оценки аналитиков:
   - **Сложность:** 🟢 низкая (до часа, точечная правка) · 🟡 средняя (несколько мест, новая логика) · 🔴 высокая (переработка, риски, новые зависимости).
   - **Польза:** ★★★ высокая (заметно пользователю или устраняет реальный риск) · ★★ средняя · ★ низкая (приятная мелочь).
4. **Сортируй от лучшего к худшему**: по пользе на единицу сложности — ★★★🟢 → ★★★🟡 → ★★🟢 → ★★★🔴 → ★★🟡 → ★🟢 → ★★🔴 → ★🟡 → ★🔴; внутри одной группы выше «Claude + Codex». Оставь 5–15 лучших пунктов.
5. Если аналитики противоречат друг другу (один советует X, другой — обратное), выбери вариант по коду и коротко отметь расхождение в пояснениях.

## 4. Результат (по-русски)

1. Одна строка: тема, что проанализировано, кто участвовал (Claude Fable, Codex или только один и почему), были ли веб-поиски.
2. Таблица:

| № | Предложение | Где | Зачем | Сложность | Польза | Автор |
|---|-------------|-----|-------|-----------|--------|-------|
| 1 | кратко, что сделать | `файл:строка`, модуль или компонент | кратко, какую проблему решает или что даёт | 🟢 низкая | ★★★ | Claude + Codex |

   Ячейки — по одной короткой фразе, без переносов строк и без `|` внутри текста. «Где» — самое короткое точное место изменения: `файл:строка`, файл, папка или компонент (для нового кода — где он появится, например «новый `src/sync.ts`»). «Автор» — `Claude`, `Codex` или `Claude + Codex`.
3. Под таблицей — не больше 3–5 строк пояснений: как внедрять неочевидные пункты (`№ — подход`) и существенные расхождения аналитиков. Одной строкой — сколько предложений отброшено при проверке и почему (например, «отброшено 4: 2 уже реализованы, 2 неприменимы»). Источники из веба, если они повлияли на предложения, — коротко ссылками.
4. Последняя строка: «Скажите номера пунктов — внедрю (например, через /dorabotay)».
