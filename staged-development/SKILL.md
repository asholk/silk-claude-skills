# Поэтапная разработка

Ты — оркестратор. Сам исследуешь, раздаёшь задачи субагентам, следишь за ними и коммитишь. **План и ревью по умолчанию делает Codex** (GPT-6-Astra, усилие high, песочница только чтение), а ты проверяешь его результат и принимаешь решения. Код задач пишут субагенты; ты сам правишь только мелочи после ревью и разрешаешь конфликты.

**Когда не Codex — Fable.** Если пользователь попросил планировать или ревьюить «без Codex» / «моделью Claude», если Codex не найден (`which codex`), упал, вернул пустой ответ или упёрся в лимит («out of credits», «usage limit») — план и ревью делают субагенты Claude **на модели Fable**: `Agent` с `model: "fable"`, `effort: "high"` (план — `subagent_type: "Plan"`, ревью — `general-purpose`). Сам план не составляй и сам не ревьюй: твоя роль — проверить результат Fable. Это правило важнее раскладки моделей из скила `optimum`. Другую модель бери, только если пользователь назвал её явно. О переходе на запасной вариант один раз скажи пользователю.

**Как запускать Codex** (общий шаблон для плана и ревью):

```bash
codex --search exec --skip-git-repo-check -m gpt-6-astra -c model_reasoning_effort=high -s read-only \
  -C "<корень репозитория>" -o "<scratchpad>/<файл>.md" - <<'EOF'
<промпт>
EOF
```

`--search` (веб-поиск) — флаг верхнего уровня, ставь его **до** `exec`; для ревью его можно опустить. Запускай через `Bash` с `run_in_background: true` и таймаутом не меньше 20 минут, результат читай из файла `-o`. Codex не видит этот разговор — промпт должен быть самодостаточным.

**Перед любой сборкой — дождись чужих сборок.** На машине параллельно работают другие сессии и процессы; одновременные сборки конфликтуют (XGE/Incredibuild отвечает «Maximum number of concurrent builds reached», UBT ждёт мьютекс или падает, линковка ловит заблокированные файлы). Поэтому перед каждым запуском сборки (своей или субагентской):
1. Проверь, не идёт ли сборка в других процессах, и если идёт — дождись окончания. Запускай ожидание фоном (`PowerShell`, `run_in_background: true`, таймаут до 60 минут) — уведомление придёт, когда чужие сборки закончатся:

   ```powershell
   $names = 'UnrealBuildTool','MSBuild','cl','link','lld-link','xgConsole','BuildConsole','AutomationTool','ninja','cmake','gradle','xcodebuild'
   while ($true) {
     $busy = Get-CimInstance Win32_Process | Where-Object {
       $_.ProcessId -ne $PID -and $_.CommandLine -notmatch 'Get-CimInstance' -and (
         $names -contains [IO.Path]::GetFileNameWithoutExtension($_.Name) -or
         ($_.Name -eq 'dotnet.exe' -and $_.CommandLine -match 'UnrealBuildTool|\bbuild\b|msbuild') -or
         ($_.Name -eq 'cmd.exe' -and $_.CommandLine -match '\\(Build|RunUAT)\.bat'))
     }
     if (-not $busy) { "{0:HH:mm:ss} no builds running" -f (Get-Date); break }
     "{0:HH:mm:ss} waiting for: {1}" -f (Get-Date), (($busy | ForEach-Object { "$($_.Name)#$($_.ProcessId)" }) -join ', ')
     Start-Sleep -Seconds 30
   }
   ```

   Список имён дополни инструментами сборки проекта (например, `node` с `webpack`/`vite build`, `cargo`, `go build`).
2. Пока ждёшь — не стартуй свою сборку и не завершай чужие процессы. Скажи пользователю одной строкой, чью сборку ждёшь (имя и PID).
3. Сразу после окончания ожидания запускай свою сборку. Если она всё же упала из-за параллельной сборки (мьютекс, «concurrent builds», занятые файлы) — повтори пп. 1–3, а не меняй код.
4. Unreal Engine: открытый редактор **этого же** проекта с Live Coding блокирует сборку — проверь командную строку `UnrealEditor.exe` (путь к `.uproject`); редактор другого проекта не мешает. Если блокирует — попроси пользователя закрыть, сам не закрывай.

Порядок фаз неизменен: **0 Исследование → 1 План → 2 Реализация волнами (+ мониторинг): код + тесты, проверка только сборкой → 3 Коммит задачи** (после каждой задачи) → **4 Финальная проверка: ревью всех задач и прогон всех тестов, исправления** (один раз, когда ВСЕ задачи реализованы) → **5 Итог**.

**Главное правило фаз 2–4.** Каждая задача пишет код **и тесты к нему**, но тесты в ходе реализации **не запускаются**, а ревью не проводится: проверка задачи — только успешная сборка/компиляция (включая тестовые файлы). Ревью и прогон тестов — один общий проход после выполнения всех задач. Так исполнители не ждут друг друга, очередь сборок и тестов не растёт, а ревьюер видит систему целиком.

## Фаза 0. Исследование (только если не хватает контекста)

Пропусти фазу, если код, затронутый задачей, уже прочитан в этом разговоре и способ реализации очевиден.

Иначе:
1. Определи вопросы, без ответа на которые нельзя спланировать: где живёт нужная логика, какие есть точки расширения, как устроены тесты и сборка, какие соглашения кода (стиль комментариев, имена, язык сообщений), есть ли похожая готовая реализация.
2. Узкие вопросы (известен файл/символ) — ищи сам (Grep/Glob/Read). Широкие — запусти **параллельно** несколько субагентов `Explore` (по одному на независимый вопрос, в одном сообщении), каждому — конкретный вопрос и ожидаемую форму ответа (пути, сигнатуры, 5–15 строк выводов, не дампы файлов).
3. Если есть альтернативы реализации — коротко сравни (1–3 варианта), выбери и обоснуй одной строкой. Спрашивай пользователя (AskUserQuestion) только если выбор действительно за ним (поведение продукта, необратимые действия), а не технический.
4. Зафиксируй факты, которые понадобятся исполнителям: команды сборки/тестов/линта, правила стиля, «опасные» места.

## Фаза 1. План

**По умолчанию план составляет Codex** (шаблон запуска — выше, `-o "<scratchpad>/plan-codex.md"`). Промпт для Codex:
- задача пользователя дословно и контекст из разговора, которого нет в коде (цели, ограничения, отвергнутые варианты);
- факты из фазы 0: ключевые файлы, команды сборки/тестов, соглашения, опасные места, выбранный вариант реализации;
- требования к плану — всё из разделов «Структура», «Объём контекста» и «Пересечения сущностей» ниже (поля задачи, шкала S/M/L, правило пересечений, волны);
- формат ответа — markdown: таблица задач с полями из «Структуры», затем разбивка на волны, затем риски и открытые вопросы;
- «ничего не изменяй».

Пока Codex (или Fable) планирует, не составляй план параллельно сам — дождись результата. Затем **проверь план**: пути и сущности существуют (Glob/Grep), пересечения «Сущностей» внутри волны действительно отсутствуют, зависимости не циклятся, оценки контекста правдоподобны, цель каждой задачи проверяема. Исправь найденное сам (кратко отметь, что поменял относительно Codex). Если Codex недоступен или пользователь попросил — план составляет субагент Fable (`Agent`, `subagent_type: "Plan"`, `model: "fable"`, `effort: "high"`) по тому же промпту, `-o` заменяется на «верни план целиком в ответе»; проверяешь его так же.

Итоговый план сохрани файлом (scratchpad-папка сессии, иначе `.claude/plans/<slug>.md` в репозитории — не коммить его). Покажи пользователю краткую версию (таблицу задач) и **продолжай без ожидания**, если пользователь не просил согласовывать план.

### Структура
- **Этапы** — логические вехи (например «Модель данных», «UI», «Интеграция»). Этап N+1 начинается после завершения этапа N, только если зависит от него.
- **Задачи** внутри этапа — единица работы одного субагента и одного коммита.

Для каждой задачи укажи:

| Поле | Что писать |
|---|---|
| ID | `S1.T2` |
| Цель | что должно работать после задачи, проверяемо |
| Сущности | файлы / модули / классы / публичные API, которые задача **меняет** (создаёт, правит, удаляет) |
| Читает | что нужно только прочитать |
| Зависит от | ID задач, результат которых нужен |
| Контекст | оценка объёма (см. ниже) |
| Проверка | какие тесты задача **пишет** (файлы, сценарии) и какая сборка подтверждает, что код и тесты компилируются; запуск тестов — в фазе 4 |
| Оценка времени | минуты (для ETA) |

### Объём контекста — определи сам
Оцени для каждой задачи, сколько кода исполнитель должен держать в голове: число и размер файлов для чтения (≈ 1 токен на 3–4 символа; строки × ~10 токенов), плюс объём изменений.
- **S** (< 20k токенов): 1–3 небольших файла — один субагент, модель по умолчанию.
- **M** (20–60k): несколько модулей — один субагент, в промпте перечисли точные файлы и фрагменты (строки), чтобы он не читал лишнее.
- **L** (60–120k): разбей задачу на подзадачи; если не делится — один субагент с жёстким списком файлов.
- **> 120k**: обязательно дроби.
Так же оцени этап целиком: если суммарный контекст этапа велик, параллель субагентов предпочтительнее одного агента.

### Пересечения сущностей
Две задачи **пересекаются**, если их множества «Сущности» имеют общий файл (или одна меняет публичный API, который другая использует). Пересекающиеся задачи — в разные волны (последовательно) или объедини в одну задачу. Общие «узкие места» (реестры, индексные файлы, `package.json`, общий CSS, главный класс на тысячи строк) — отдельной короткой задачей-интеграцией в конце этапа, а не правкой из нескольких задач сразу.

## Фаза 2. Реализация волнами

1. Разбей задачи этапа на **волны**: в волне — задачи без пересечений сущностей и с выполненными зависимостями.
2. Запусти задачи волны **параллельно** — несколько вызовов `Agent` в одном сообщении (`subagent_type: "general-purpose"`, по умолчанию та же модель). Если задачи волны всё же могут задеть общие файлы косвенно (генерация, форматтер) и репозиторий — git, используй `isolation: "worktree"` и затем слей изменения сам.
3. **Промпт субагента** должен быть самодостаточным (он не видит этот разговор):
   - цель задачи и критерий готовности;
   - точный список файлов, которые **можно менять**, и запрет трогать остальные (особенно сущности других задач волны);
   - что прочитать (пути и, по возможности, строки);
   - соглашения проекта из фазы 0 (стиль, язык сообщений, комментарии как в окружающем коде);
   - **написать тесты** к реализованному коду (сценарии из поля «Проверка» плана) в принятом в проекте стиле, но **не запускать их** и не проводить ревью;
   - проверка — только сборка/компиляция (код и тестовые файлы должны компилироваться; типы/линт — если быстрые); приложить результат;
   - перед сборкой — дождаться чужих сборок (вставь в промпт правило «Перед любой сборкой» вместе с командой ожидания); если задачи волны собирают один и тот же проект, субагенты не собирают — сборку после волны делает оркестратор; ошибки в файлах соседних задач волны не чинить, а перечислить;
   - **не коммитить** (коммитит оркестратор) и не запускать долгие/интерактивные процессы;
   - формат отчёта: изменённые файлы (отдельно — тестовые), что сделано (3–7 пунктов), результат сборки, раздел «Для этапа тестов» (что проверяют тесты, хрупкие места, где ожидания могут потребовать правок), открытые вопросы и что нужно сделать в чужих файлах.
4. Запиши для каждой задачи время старта (для ETA и мониторинга).
5. Когда приходит уведомление о завершении субагента — проверь, что сборка прошла и тесты написаны, затем сразу переходи к фазе 3 (коммит) для этой задачи, не дожидаясь остальных в волне. Следующую волну запускай, как только освободились её зависимости. Требования задачи к чужим файлам («подключить в …») собирай в общий файл заметок рядом с планом и передавай владельцам/интеграционной задаче.
6. Субагент сообщил о проблеме или не уложился — дай уточнение через `SendMessage` тому же агенту (контекст сохранён) или перезапусти с исправленным промптом. Не выдумывай результат незавершённого агента.

### Мониторинг (каждые 15 минут)

Сразу после запуска первой волны заведи периодическую проверку:
- Загрузи `CronCreate` (через `ToolSearch`, `select:CronCreate,CronDelete,CronList`) и создай задание с расписанием `*/15 * * * *` и промптом «Мониторинг staged-development: проверь живость субагентов и выдай отчёт по плану <путь к плану>».
- Если `CronCreate` недоступен — используй `Monitor` (если есть) с периодом 15 минут; если нет и его — давай отчёт при каждом уведомлении о завершении субагента и предупреди пользователя, что периодических отчётов не будет.

На каждом срабатывании:
1. **Живость:** `ListAgents` / статусы фоновых задач. Агент «жив», если в работе; «завис», если нет новых событий дольше 2× его оценки времени — тогда напиши ему через `SendMessage` (запрос статуса) или перезапусти задачу, и отметь это в отчёте.
2. **Отчёт пользователю** — короткая таблица и итоговая строка:

```
| Задача | Агент | Статус | Прошло | ETA задачи |
|---|---|---|---|---|
| S1.T1 Модель данных | impl-a | ✅ готово, закоммичено | 12 мин | — |
| S1.T2 API | impl-b | 🔄 в работе | 18 мин | ~10:42 |
| S1.T3 UI | — | ⏳ ждёт S1.T2 | — | ~11:05 |
| S2.T1 Интеграция | — | ⏳ этап 2 | — | ~11:30 |

Готово 1/4 · ревью/исправления: 0 · проблемы: нет · **общее окончание ≈ 11:30**
```

   Статусы: ⏳ ждёт · 🔄 в работе · 🔍 ревью · 🛠 исправления · ✅ готово · ⚠️ проблема / завис.
3. **ETA:** для задачи в работе — старт + оценка × коэффициент. Коэффициент = (фактическое время завершённых задач) / (их оценка), начиная с 1.0. Для ожидающих — время готовности зависимостей + их оценка × коэффициент (+ ~10 % на коммит). Общее окончание — максимум ETA по последнему этапу плюс оценка финальной проверки (ревью и тесты, обычно 20–40 % от суммарного времени реализации). Указывай абсолютное местное время (`date`) и «≈».
4. Когда все задачи завершены — удали задание мониторинга (`CronDelete`).

## Фаза 3. Коммит (после каждой задачи)

1. Только если это git-репозиторий. Если текущая ветка — основная (`main`/`master`/дефолтная) и пользователь не сказал коммитить прямо в неё — один раз в начале создай ветку `feature/<slug>`.
2. Добавляй **только файлы этой задачи** (`git add <пути>`), не `git add -A`: параллельные задачи и чужие изменения в рабочем дереве не должны попасть в коммит. Проверь `git diff --cached --stat` перед коммитом.
3. Не пропускай хуки (`--no-verify` запрещён). Хук упал — исправь причину и создай коммит заново.
4. Сообщение — заголовок в стиле Conventional Commits и категоризированное тело. Язык — как в истории репозитория (по умолчанию русский):

   ```
   feat(scope): кратко, что появилось — до ~72 символов

   ✨ Добавлено
   - …
   🐛 Исправлено
   - …
   ♻️ Переработано
   - …
   ⚡ Производительность
   - …
   🧪 Тесты
   - …
   📝 Документация
   - …

   Задача: S1.T2 · План: <Codex GPT-6-Astra high / Claude Fable> · Тесты написаны, не запускались; ревью — в финальной проверке
   ```

   Тип заголовка: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore`, `build`. Пустые категории не пиши. Каждый пункт — одна строка, по сути изменения, без перечисления файлов. В конце — строки атрибуции, если их требует системная инструкция сессии.
5. Передавай сообщение через heredoc (`git commit -F - <<'EOF' … EOF`), чтобы не ломались кавычки и переводы строк. Пуш — только если пользователь просил.
6. Не git (Perforce и т. п.) или VCS недоступна из консоли — не коммить; в конце подготовь описание changelist (тот же формат, с пометкой о состоянии тестов и ревью) и список файлов для add/checkout, сообщи пользователю.

## Фаза 4. Финальная проверка: ревью и тесты (после выполнения ВСЕХ задач)

Начинай, только когда все задачи плана реализованы, закоммичены и полная сборка проходит.

1. **Полная сборка** (после ожидания чужих сборок) — зелёная, без новых предупреждений.
2. **Ревью — один общий проход по всем задачам, параллельно.** Раздели изменения на 3–8 групп по областям (например, по этапам или подсистемам) и запусти ревью групп одновременно. Ревьюер по умолчанию — Codex (шаблон запуска — выше, без `--search`, `-o "<scratchpad>/review-<группа>.md"`). Промпт:

   ```
   Сделай код-ревью изменений <группа>: <цели задач группы>.
   Дифф: git diff <база>..HEAD -- <файлы> (или файлы: <список>, если не git); прочитай окружающий код, если нужно.
   Найди только существенное: ошибки, граничные случаи, регрессии, стыки между задачами, безопасность, несоответствие цели, стиль проекта, пробелы в тестах. Без вкусовщины.
   Формат: «серьёзность · файл:строка · проблема · как исправить» по строке на находку; если замечаний нет — «замечаний нет».
   Ничего не изменяй.
   ```

   **Запасной ревьюер** — если Codex недоступен (не найден, упал, пустой ответ, закончились кредиты/лимит — «out of credits», «usage limit») или пользователь попросил ревью без Codex: свежие субагенты `general-purpose` с `model: "fable"`, `effort: "high"` (другая модель — только если пользователь назвал её явно), без истории реализации, тот же промпт; все группы — в одном сообщении, параллельно. Повторный раунд ревью в п. 5 — тем же ревьюером.
3. **Прогон всех тестов** — параллельно с ревью или сразу после (не мешает сборкам ревьюеров: ревью ничего не собирает). Запусти полный набор тестов проекта, собери результаты с числами (прошло/упало/пропущено) и тексты падений.
4. **Разбор и исправления.** Проверь находки ревью и падения тестов сам (прочитай код): ложные отбрось с пометкой; падение теста раздели на «баг реализации» и «неверное ожидание теста». Исправления раздай субагентам по областям файлов (без пересечений, волнами как в фазе 2), мелочи правь сам. Каждый исправитель — пересобирает и прогоняет тесты своей области.
5. **Повтор.** Полная сборка и полный прогон тестов; при существенных исправлениях — короткий повторный раунд ревью только по ним. Не больше 2 раундов; оставшееся вынеси в итог как известные ограничения.
6. **Коммиты исправлений** — по правилам фазы 3, тип `fix`/`test`, с пометкой «Финальная проверка · ревью: <Codex GPT-6-Astra high / Claude Fable>, замечаний исправлено: N · тесты: X/Y».

## Фаза 5. Итог

Когда все этапы закрыты:
- финальная таблица задач (статус, коммит `short sha`, время факт/оценка);
- общий результат финальной проверки (сборка; тесты — с реальными числами; число замечаний ревью найдено/исправлено/отброшено);
- что не сделано или вынесено (с причиной), найденные, но не исправленные проблемы;
- удалено ли задание мониторинга.

Пиши кратко; пользователь читает итог, а не процесс.

## Правила

- Не запускай параллельно задачи, меняющие один файл. Сомневаешься в пересечении — последовательно.
- В фазе 2 тесты только пишутся; запуск тестов и ревью — только в фазе 4, после всех задач.
- Сборки — инкрементальные: если код копируется в отдельное место сборки, сохраняй даты файлов (`cp -p`/`rsync -t`), иначе каждая сборка становится полной.
- Никакой сборки, пока в системе идёт другая: сначала ожидание (см. «Перед любой сборкой»), потом своя.
- Не выдумывай статусы и результаты субагентов: «ещё работает» — значит ещё работает.
- Не расширяй объём работ сверх плана; новые находки — в итог или отдельной задачей с согласия пользователя.
- Деструктивные действия (удаление файлов пользователя, `reset --hard`, force-push, миграции данных) — только с подтверждением пользователя.
- Если задача маленькая (один-два файла, < 30 минут) — скажи, что поэтапный процесс избыточен, и сделай напрямую, если пользователь не настаивает.
