# Концепт

Запрос пользователя: **$ARGUMENTS**

> При запуске субагентов и Codex следуй скилу `optimum` (§2 модели, §3 промпт, §7 Codex); если он не установлен — модели указаны ниже.

Ты координатор. Идеи ищут два независимых исследователя — субагент Claude и Codex. Ты ставишь задачу, отбираешь лучшее, формируешь три предложения, заказываешь иллюстрации и сам собираешь сайт.

Файлы скила:
- `design.md` — справочник оформления: каркас предложения, структура лендинга, схемы, промпты картинок, стиль. **Прочитай его перед шагом 3.**
- `gen_images.py` — генерация картинок через Codex (встроенный image_gen).

Путь к папке скила: `~/.claude/skills/concept/` (на Windows `C:\Users\<user>\.claude\skills\concept\`).

## 1. Тема и бриф

1. Из запроса определи **предмет концепта** (продукт, сервис, фича, бизнес-идея, мероприятие…), аудиторию и цель. Если запрос пустой — возьми то, что обсуждалось в разговоре последним. Уточняющих вопросов не задавай: тему назови одной строкой в начале ответа.
2. Если концепт про текущий проект — коротко сориентируйся (Glob/Grep, 2–5 вызовов), чтобы передать исследователям контекст.
3. Придумай **slug** — короткое латинское имя в kebab-case. Папка сайта: `<рабочая папка>/Concept/<slug>/`. Если она существует — суффикс `-2`, `-3`…; существующие файлы не перезаписывай.
4. Составь **бриф** — один текст для обоих исследователей, сохрани его в `<scratchpad>/concept-brief.md`:
   - предмет, аудитория, цель, ограничения, контекст из разговора; всё, что пользователь явно попросил учесть (технологии, платформы, партнёры), — отдельным обязательным пунктом;
   - задача: 4–8 целевых веб-поисков — лучшие практики, решения лидеров рынка, удачные кейсы, исследования, типичные ошибки; на этой основе **3–5 принципиально разных концепций** (разные подходы, аудитории, модели, а не вариации одного);
   - для каждой концепции: название · positioning по формуле «Для [кого], у кого [боль], [название] — это [категория], которая [польза]. В отличие от [альтернатива], [отличие]» · job story «Когда…, я хочу…, чтобы…» · 3–5 ключевых возможностей · reason to believe (почему сработает) · why now · альтернативы и отличие от них · модель (цена, формат) · главный риск и что проверить первым · идея-фишка · 2–3 сцены использования (кто, где, что делает — для иллюстраций);
   - для каждой концепции — паспорт различий по §3а: механизм, сценарий взаимодействия, формат результата, способ предоставления ценности и сознательный компромисс;
   - отдельно — 5–10 лучших практик, полезных для любого варианта;
   - реальные возможности и ограничения названных технологий подтверждать документацией; что не подтверждено — помечать «проверить»;
   - источники ссылками; ничего не создавать и не менять в файлах.

## 2. Два исследователя параллельно, в фоне

Запусти обоих **в одном сообщении**, оба в фоне.

- **Claude** — `Agent` с `subagent_type: general-purpose`, `run_in_background: true`, `model` и `effort` — по таблице ролей optimum §2 (без optimum — `sonnet` `high`); промпт: прочитать бриф из файла и выполнить, веб-поиск через `ToolSearch "select:WebSearch,WebFetch"`.
- **Codex** — GPT-6-Astra, усилие high, только чтение, с веб-поиском; запуск — по шаблону optimum §7, если он установлен. Автономная команда (флаг `--search` — верхнего уровня, стоит **до** `exec`; через `Bash` с `run_in_background: true`, таймаут не меньше 20 минут):

  ```bash
  S="<scratchpad>"
  codex --search exec --skip-git-repo-check -m gpt-6-astra -c model_reasoning_effort=high -s read-only     -C "<рабочая папка>" -o "$S/concept-codex.md" - < "$S/concept-brief.md" > "$S/concept-codex.log" 2>&1
  ```

  Промпт — бриф `concept-brief.md`, результат — `concept-codex.md`.

Коротко сообщи пользователю, что исследование запущено, и дождись уведомлений — сам ту же тему не исследуй. Если Codex не найден, упал или вернул пустой ответ — один раз скажи об этом и продолжай с Claude; если упал субагент — продолжай с Codex.

## 3. Синтез: три предложения

Прочитай `design.md`.

1. Объедини концепции обоих исследователей; совпавшие по механике идеи считай одной группой, оставляя одного представителя. Совпадение не является независимым доказательством качества. Отбрось слабые, нереалистичные и неотличимые.
2. Сформируй **ровно 3 предложения**, прошедших проверку §3а. Ярлыки «проверенный / смелый / нишевый» не доказывают различие. Общие практики качества переносить можно; перенос отличительных фишек требует повторной попарной проверки, чтобы не превратить варианты в один набор возможностей.
3. Для каждого заполни **каркас** из `design.md` §1 (positioning, заголовок до 10 слов, подзаголовок, job story, insight, 3 пользы, RTB, why now, альтернативы, риск и что проверить, модель) и контент секций лендинга из §2. Пройди тест 5 секунд для каждого hero.
4. Выбери для каждого лендинга 2–3 типа схем из §3 — разные у разных предложений, по смыслу (у носимого устройства — «до/после», у системы с участниками — экосистема, у ритуала — таймлиния дня).
5. Для главной: оценки 1–5 по 4–5 одинаковым критериям, оси матрицы 2×2, рекомендация, источник идеи (Claude / Codex / Claude + Codex).
6. Тексты — на языке запроса, конкретные: сцены, цифры, глаголы; без «инновационная платформа» и «Lorem ipsum».

## 3а. Обязательная проверка различий до оформления

Три концепта — самостоятельные способы решить исходную задачу. Разные названия, цвета, формулировки, цены и количество функций сами по себе не считаются различием. «Базовый / расширенный / премиум» одного решения — тарифы, а не разные концепты.

1. Зафиксируй общую цель и неизменяемые требования пользователя. Выбери 3–5 свободных содержательных осей: механизм решения; сценарий взаимодействия и распределение ролей; формат результата; способ предоставления ценности; необходимая инфраструктура. Аудиторию меняй только если пользователь её не зафиксировал. Не считай два следствия одного изменения независимыми осями.
2. Составь таблицу «ось → вариант 1 / вариант 2 / вариант 3» с конкретными решениями. Каждая пара **1–2, 1–3, 2–3** должна различаться минимум по двум независимым осям, причём хотя бы одна — механизм решения или основной сценарий взаимодействия. Объясни наблюдаемое последствие: что пользователь или система реально делает иначе. Три взаимодополняющих модуля одного продукта не заменяют три самостоятельных решения.
3. Для каждого варианта укажи отличительную механику, конкретный сценарий, сознательный компромисс и ситуацию, в которой его предпочтут двум другим. Все варианты должны быть жизнеспособны в рамках брифа: не добавляй заведомо слабый ради контраста. Разные числа цены или скорости без разного устройства решения не проходят проверку.
4. Тест без названий: убери брендинг, оценочные прилагательные, цены и оформление. Если остаётся одинаковая последовательность действий с той же механикой — это дубли. Тест переноса: если ключевой сценарий и объясняющую схему можно перенести в соседний вариант простой заменой названий, содержательное различие ещё не показано.
5. Если хотя бы одна пара не прошла, переработай или замени дублирующий вариант по свободной оси и перепроверь все пары. До прохождения проверки не заказывай иллюстрации и не верстай лендинги. Не более двух раундов переработки. Если ограничения не оставляют места для трёх самостоятельных решений, выдай только прошедшие варианты, объясни ограничение и укажи, какое требование нужно ослабить. Не нарушай бриф ради разнообразия. Это исключение из требований «ровно 3» и «9 картинок»: количество лендингов, строк сравнения и комплектов иллюстраций соответствует фактическому числу вариантов.
6. На главной покажи компактную таблицу различий и одну фразу о решающем отличии каждой пары. Оценки качества 1–5 её не заменяют. После подготовки текстов, схем и сцен повтори тесты: оформление и перенос лучших практик не должны стирать различия.

Пример брака: три планировщика с одинаковым ручным списком задач, разными названиями и числом напоминаний. Возможные разные механики: ручное планирование дня; автоматическое распределение задач по свободным интервалам; согласование задач участниками через общую очередь. Такой набор подходит только если каждый способ решает исходную задачу в рамках брифа; различия подтверждаются сценариями и компромиссами, а не названиями.

## 4. Иллюстрации через Codex (в фоне)

Сразу после синтеза, **до** вёрстки:

1. Определи палитру сайта (фон, текст, 3 акцента предложений) и составь **style block** по `design.md` §4 — один на весь концепт, палитра совпадает с CSS-токенами. Персонажей опиши один раз и повторяй дословно.
2. Запиши `<scratchpad>/concept-images.json`:

   ```json
   {
     "style": "Minimal flat editorial illustration, ... palette: warm off-white #fbfaf7, charcoal #1d1c1a, orange #d9692b, teal #2f7d6d, indigo #4a5bd4 ...",
     "avoid": "text, letters, numbers, logos, watermarks, brand names, photorealism, stock-photo look, clutter",
     "images": [
       {"name": "offer-1-hero",    "aspect": "16:9", "prompt": "..."},
       {"name": "offer-1-scene-1", "aspect": "4:3",  "prompt": "..."},
       {"name": "offer-1-scene-2", "aspect": "4:3",  "prompt": "..."}
     ]
   }
   ```

   9 картинок: hero + 2 сцены на каждое предложение. У каждого варианта — собственные действие, ключевой объект и композиция, объясняющие его механику из §3а; смена акцентного цвета не подходит. Общий художественный стиль сохраняется. Промпты на английском, по одной мысли, без текста на картинке и без названий брендов.
3. Запусти в фоне (`Bash`, `run_in_background: true`, таймаут 40 минут; 2 картинки параллельно, одна ≈1 минута):

   ```bash
   python -I ~/.claude/skills/concept/gen_images.py "<scratchpad>/concept-images.json" \
     --out "<папка сайта>/img" --work "<scratchpad>/concept-img-work"
   ```

   Флаги: `--only имя1,имя2` — перегенерировать выбранные, `--replace` — перезаписать, `--dry-run` — показать промпты. Итог — `img/<name>.jpg` и `img/images.json` со статусами; лог каждой картинки — в `--work/<name>/`.
4. Пока картинки генерируются — верстай сайт (шаг 5), ссылаясь на будущие `img/<name>.jpg`.
5. После уведомления открой каждый JPG через Read и проверь: нет текста и букв, стиль един, сюжет читается, нет уродств. Брак — **одна** перегенерация с поправленным промптом (`--only … --replace`). Картинку, которая так и не получилась, замени на схему или акцентный блок — битых ссылок быть не должно.

Если Codex недоступен — сайт делается без картинок, только со схемами; скажи об этом в ответе.

## 5. Сайт

```
Concept/<slug>/
  index.html     — главная-сравнение
  offer-1.html   — лендинг предложения 1
  offer-2.html   — лендинг предложения 2
  offer-3.html   — лендинг предложения 3
  style.css      — общие стили
  img/           — иллюстрации Codex + images.json
```

- Структура главной и лендингов — `design.md` §2; на каждом лендинге обязательны **«Коротко о сути»** сразу под hero, **минимум 2 SVG-схемы** и **3 иллюстрации** (hero + раскадровка из 2 кадров с подписями).
- Схемы — inline SVG по правилам `design.md` §3 (цвета через `var(--…)`, `role="img"`, `aria-label`, читаемость на 360px). Проверь геометрию.
- Стиль — `design.md` §5: минимализм, тёмная тема, адаптивность, чистый HTML + CSS, относительные ссылки.
- Навигация: на лендингах — «← Все предложения» и соседние предложения; на главной карточки ведут на лендинги и показывают hero-миниатюру.
- Подвал главной: дата, кто участвовал (Claude, Codex, картинки — Codex image_gen), источники.

Проверка перед ответом:
- все пары прошли §3а; таблица различий соответствует фактическим текстам, схемам и сценам;
- все файлы на месте; каждая ссылка `href`/`src` указывает на существующий файл (скриптом: собрать `href="…"` и `src="…"` и проверить `test -f`);
- нет пустых мест, «TODO», «Lorem»;
- если доступен браузер (Claude in Chrome или встроенный) — `file://` он не открывает: подними `python -m http.server <порт> --bind 127.0.0.1` в папке сайта (в фоне), проверь страницы на 375px и ~1100px по `design.md` §3 (нет горизонтальной прокрутки, подписи схем не мельче 13px и не пересекаются), затем останови сервер и закрой вкладку; не обязательно.
- Если страниц много или схемы повторяются — собирай сайт Python-скриптом в scratchpad (данные предложений + функции схем), а не вручную: так единообразнее и проще править.

## 6. Ответ (по-русски, кратко)

1. Тема одной строкой и кто участвовал (Claude, Codex; сколько картинок сгенерировано, были ли перегенерации или пропуски).
2. Предложения с решающим отличием каждого — по строке (при исключении §3а укажи фактическое число и причину ограничения): `N. Название — positioning в одну фразу`.
3. Рекомендация: какое сильнее и почему, одной-двумя фразами; главный риск, который проверить первым.
4. Путь к сайту: `Concept/<slug>/index.html`.
5. Модели: исследователь Claude — <модель, effort>; Codex — <модель, effort / не запускался>; иллюстрации — Codex image_gen.
