# Доработай

Запрос пользователя: **$ARGUMENTS**

Ты — главный процесс: ставишь задачу, проверяешь результат и отчитываешься. Код пишет субагент, ревью делает отдельный субагент на модели **Fable** (другую модель — только если пользователь назвал её явно; это правило важнее раскладки из скила `optimum`). Сам код не правишь, даже мелочи: все исправления тоже идут через субагента.

## 1. Постановка задачи

1. Если в этом разговоре ещё нет нужного контекста, коротко сориентируйся (1–3 вызова Grep/Glob/Read): где живёт затронутый код и какие там соглашения. Не исследуй проект целиком.
2. Если проект — git-репозиторий, запиши базу для ревью: `git status --short` и `git rev-parse HEAD`. Изменения, которые уже были до начала работы, при ревью отделяй от новых.
3. Запусти субагента: `Agent`, `subagent_type: general-purpose`, `model: sonnet`. Субагент не видит разговора, поэтому промпт должен быть самодостаточным:
   - запрос пользователя и твоё понимание, что именно нужно сделать;
   - пути к файлам, имена классов и методов, известные по разговору; сделанные ранее решения, которые нельзя ломать;
   - правила работы субагента (блок ниже) — передай его целиком.
4. Дождись уведомления о завершении. Не делай работу параллельно сам и не придумывай результат до уведомления. Сообщи пользователю одной строкой, что задача запущена.

### Правила для субагента (вставь в промпт)

> - Найди нужный код за минимум шагов: Grep/Glob по ключевым словам, читай только нужные фрагменты.
> - Неоднозначность реши сам: выбери самое разумное толкование, соответствующее существующему коду, и укажи его в отчёте. Не останавливайся ради уточнений.
> - Правь точечно, в стиле окружающего кода: те же имена, идиомы, язык сообщений интерфейса и плотность комментариев. Без рефакторинга и без того, о чём не просили.
> - Запусти самую дешёвую доступную проверку: синтаксис (`node --check`, `python -m py_compile` и т. п.), сборку, линтер или затронутые тесты. Если что-то сломалось — исправь.
> - Перед сборкой проверь, не идёт ли сборка в других процессах (команда ожидания ниже, фоном). Если идёт — дождись окончания, потом запускай свою; чужие процессы не завершай. Если своя сборка упала из-за параллельной (мьютекс, «concurrent builds», занятые файлы) — дождись и повтори, код не меняй.
> - Не коммить, не пушь, не удаляй чужие файлы.
> - Отчёт: что сделано, список изменённых файлов, как проверено и что проверить не удалось, принятые допущения.

## Сборка: сначала дождись чужих

Другие сессии и процессы могут собирать параллельно; одновременные сборки конфликтуют (XGE «Maximum number of concurrent builds reached», мьютекс UBT, занятые при линковке файлы). Перед каждой сборкой — своей и субагентской (передай ему этот раздел вместе с командой):
1. Запусти ожидание фоном (`PowerShell`, `run_in_background: true`, таймаут до 60 минут) и дождись уведомления:

   ```powershell
   $names = 'UnrealBuildTool','MSBuild','cl','link','lld-link','xgConsole','BuildConsole','AutomationTool','ninja','cmake','gradle','xcodebuild'
   while ($true) {
     $busy = Get-CimInstance Win32_Process | Where-Object {
       $_.ProcessId -ne $PID -and $_.CommandLine -notmatch 'Get-CimInstance' -and (
         $names -contains [IO.Path]::GetFileNameWithoutExtension($_.Name) -or
         ($_.Name -eq 'dotnet.exe' -and $_.CommandLine -match 'UnrealBuildTool|\bbuild\b|msbuild') -or
         ($_.Name -eq 'cmd.exe' -and $_.CommandLine -match '\\(Build|RunUAT)\.bat'))
     }
     if (-not $busy) { "{0:HH:mm:ss} no builds running" -f (Get-Date); break }
     "{0:HH:mm:ss} waiting for: {1}" -f (Get-Date), (($busy | ForEach-Object { "$($_.Name)#$($_.ProcessId)" }) -join ', ')
     Start-Sleep -Seconds 30
   }
   ```

   Добавь в список инструменты сборки проекта, если их там нет.
2. Пока ждёшь — свою сборку не стартуй, чужие процессы не завершай; одной строкой скажи пользователю, чью сборку ждёшь.
3. После окончания ожидания сразу запускай свою сборку.
4. Unreal Engine: мешает только открытый редактор этого же проекта (Live Coding) — смотри путь к `.uproject` в командной строке `UnrealEditor.exe`; закрыть его попроси пользователя.

## 2. Ревью (субагент Fable + твоя проверка)

1. Посмотри фактические изменения: `git diff` относительно записанной базы. Вне git читай изменённые места в файлах из отчёта субагента. Не полагайся только на отчёт.
2. Запусти ревьюера: `Agent`, `subagent_type: general-purpose`, `model: fable`, `effort: high` — свежий контекст, без истории реализации. В промпт: запрос пользователя, база (`git diff <база>` или список изменённых файлов из отчёта), критерии из п. 4, формат ответа «критическое/некритическое · файл:строка · проблема · как исправить» по строке на находку (или «замечаний нет») и запрет что-либо менять, собирать или коммитить.
3. Пока ревьюер работает — сам перезапусти проверку (синтаксис, сборку или тесты). Сборку — только после ожидания чужих сборок (раздел «Сборка» ниже).
4. Критерии ревью (их же проверяй, когда разбираешь находки):
   - выполнен ли запрос полностью и так, как понял бы пользователь;
   - нет ли ошибок логики, падений, гонок, утечек обработчиков, потери данных;
   - не сломано ли существующее поведение рядом (клики, горячие клавиши, сохранение, другие режимы);
   - нет ли конфликтов имён с API фреймворка, вызовов несуществующих методов, пропущенных проверок на `null`.
5. Проверь каждую находку Fable по коду: ложные отбрось. Раздели оставшиеся:
   - **Критические**: баг, падение, потеря или порча данных, сломанное существующее поведение, невыполненная часть запроса, уязвимость.
   - **Некритические**: стиль, мелкие улучшения, спорные решения. Их не исправляй, только упомяни в итоге, если они важны пользователю.

## 3. Исправления (только при критических замечаниях)

1. Отправь замечания тому же субагенту через `SendMessage` (у него сохранился контекст). Если это недоступно, запусти нового с полным контекстом. Для каждого замечания укажи `файл:строка`, что не так, сценарий воспроизведения и ожидаемое поведение. Повтори правила для субагента.
2. После завершения повтори ревью только по исправленным местам — тем же ревьюером Fable (`SendMessage`) или новым с `model: fable`.
3. Не больше двух раундов исправлений. Если критическое замечание осталось — не скрывай его: опиши в итоге и предложи, что делать.

## 4. Итог пользователю (по-русски, кратко)

- **Всё хорошо:** 2–5 пунктов о том, что изменилось с точки зрения пользователя; изменённые файлы; чем проверено и что не проверялось (например, «в приложении не запускал»).
- **Были исправления:** то же самое плюс одна строка о том, что нашёл ревью и что исправлено.
- Принятые допущения и важные некритические замечания — отдельной строкой, если они есть.
- Не пересказывай процесс по шагам и не вставляй дампы кода.
